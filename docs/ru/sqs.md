# Amazon SQS

`ruststream-sqs-sns` запускает сервис RustStream на Amazon SQS и публикует через SNS всем
подписчикам разом. SQS - это очередь: доставленное сообщение либо удаляется, либо возвращается в
очередь, а момент возврата определяет тайм-аут видимости. Крейт закрывает длинный опрос, повторные
попытки по видимости, FIFO-группы сообщений и под фичей `testing` поставляет внутрипроцессный
тестовый брокер. Понятия фреймворка (как писать подписчиков, роутинг, кодеки, middleware) описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros"] }
ruststream-sqs-sns = "0.7"
serde = { version = "1", features = ["derive"] }
```

Файл сервиса импортирует `ruststream_sqs_sns::prelude::*` и больше ничего ни из одного крейта: этот
glob реэкспортирует прелюдию самого фреймворка вместе с брокером, дескриптором очереди, политиками
публикации и издателями этого крейта. Элементы фреймворка проходят через него без изменений, поэтому
сервис, работающий на двух брокерах, импортирует обе прелюдии, а общее у них разрешается в один
элемент.

MSRV крейта - 1.94.1, вслед за AWS SDK; ядро фреймворка остаётся на 1.88, а зависимый крейт вправе
стоять выше нижней границы своей зависимости.

## Совместимости {#capabilities}

Необязательные совместимости фреймворка и то, какие из них этот брокер реализует встроенно.
Совместимость, которой у брокера нет, - ошибка компиляции в точке монтирования.

| Совместимость | Встроенная | Почему |
| --- | --- | --- |
| `Subscribe` | да | хватает имени очереди: `#[subscriber("orders")]` связывает без дескриптора |
| `BatchSubscriber` | да | `ReceiveMessage` и так пакетный вызов: один приём - один пакет (см. [Пакеты](#batches)) |
| `TransactionalPublisher` | нет | в SQS нет транзакционной отправки |
| `OwnedTransactions` | нет | в SQS нет транзакционной отправки |
| `RequestReply` | нет | в SQS нет входящего ящика для ответов; ответ - обычная отправка в другую очередь |
| `Partitioned` | да | доставленное сообщение отдаёт идентификатор своей FIFO-группы в заголовке `partition-key`, а публикация читает свою группу из этого заголовка (см. [FIFO-группы сообщений](#fifo-message-groups)) |
| `Seekable` / `Positioned` | нет | у очереди нет курсора, который можно двигать; сообщения, пережившие свои попытки, достают из очереди недоставленных сообщений, которую задаёт политика перенаправления |
| `DescribeServer` | да | `SqsBroker` сообщает хост и порт, к которым подключается, и протокол `sqs` в документ AsyncAPI, который генерирует фреймворк |

## Жизненный цикл {#the-lifecycle}

Брокер - это последовательность переходов, поглощающих `self`, поэтому каждое состояние
представлено отдельным типом:

```text
SqsBroker::new()          только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedSqsBroker    живые клиенты SDK; подписки и издатели
  .shutdown()  ->  ()                    завершающий переход
```

Рантайм вызывает `connect` один раз при старте, до открытия первой подписки, и регион с учётными
данными разрешаются там из окружения (профиль, IMDS, SSO). Ввод-вывод вынесен из `new`, и поэтому
сервис на SQS собирается тем же макросом `#[ruststream::app]`, что и сервис на любом другом брокере.
`shutdown` поглощает подключённый брокер, поэтому публикация или подписка после него не
компилируется. Он же помечает разделяемое состояние клиента закрытым, поэтому издатель, выданный
раньше, возвращает `SqsError::NotConnected`, а не отрабатывает по соединению, от которого приложение
уже отказалось.

Конфигурация задаётся на синхронном билдере:

- `SqsBroker::new()` разрешает всё из окружения.
- `SqsBroker::from_config(config)` принимает готовый `aws_config::SdkConfig`; так же сервис
  закрепляет фиксированную версию поведения SDK вместо последней.
- `endpoint(url)`, `region(name)` и `test_credentials()` направляют брокер на локальный стенд. URL
  очередей, которые возвращает SQS, переносятся на настроенный endpoint, поэтому приёмы подмены
  хоста, принятые у локальных стендов, для адаптера ничего не меняют.

`connect` заодно ставит в собираемой конфигурации SDK тайм-аут одной попытки в 25 секунд - выше тех
20 секунд, которые может ждать длинный опрос.

## Дескрипторы очередей {#queue-descriptors}

`SqsQueue` описывает подписку на одну очередь. Параметры, от которых зависят стоимость и задержка,
заданы на нём явно:

| Метод | Что задаёт | По умолчанию |
| --- | --- | --- |
| `wait(Duration)` | ожидание длинного опроса на один вызов приёма, не больше протокольных 20 секунд | 20 секунд |
| `visibility(Duration)` | тайм-аут видимости, запрашиваемый на каждом приёме, в пределах `1s..=12h` | тайм-аут, настроенный у очереди |
| `create_if_missing()` | создаёт очередь при подписке, если её нет | выключено |

Размера пакета среди них нет. Он относится к регистрации: пакетный обработчик задаёт его в точке
монтирования через `batch(n)` (см. [Пакеты](#batches)).

Дескриптор проверяется до любого ввода-вывода. Пустое имя, ожидание выше предела или видимость вне
диапазона возвращают `SqsError::InvalidQueue` в момент подписки, без обращения к AWS.

Дескриптор пишется прямо в макросе `#[subscriber(..)]` и называет очередь по URL или по имени; имя
разрешается через `GetQueueUrl` и кешируется. В примерах добавлен `create_if_missing()`, потому что
они работают с локальным стендом, где ничего не заведено; боевой сервис его не ставит:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_service.rs:handler"
```

Смонтируйте его на брокере:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_service.rs:app"
```

Простая строковая форма `#[subscriber("orders")]` берёт умолчания дескриптора.
`#[subscriber(SqsQueue)]` закрепляет вид источника и оставляет имя точке монтирования -
`b.include(handler.name("orders"))`; так одно определение обработчика обслуживает две очереди.

Имя очереди, которым пользуется сервис, не обязано быть допустимым именем SQS: по пути в SQS каждый
символ вне `[A-Za-z0-9_-]` заменяется на `-`, а суффикс `.fifo` сохраняется. Подписки и публикации в
очередь пользуются одним отображением, поэтому имя фреймворка с точками остаётся маршрутизируемым на
очереди.

Те же параметры доступны и в точке монтирования, в словаре самого крейта, через трейт
`SqsSubscription` из прелюдии. Регистрация, которая сперва называет размер пакета, продолжается ими
там же, потому что шаги самого фреймворка идут в цепочке первыми:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_batches.rs:mount"
```

Очередь, которую приходится создавать `create_if_missing`, - стандартная очередь, а при имени
на `.fifo` - FIFO-очередь с дедупликацией по содержимому. Боевыми очередями обычно управляют
как инфраструктурой.

Подписка - это поток, который наполняет фоновая задача, опрашивающая `ReceiveMessage` длинным
опросом. Её канал вмещает один пакет, поэтому задача не уходит больше чем на один приём вперёд от
того, что вычитывает обработчик. Уничтожение потока останавливает задачу; сообщения, которые она
уже доставила и которые никто не завершил, доставляются снова, когда истечёт их видимость. Ошибки
приёма попадают в поток его элементами: несуществующая очередь завершает поток, а любая другая
ошибка выдерживает паузу в секунду, поэтому постоянная ошибка не может раскрутить цикл вхолостую.

## Пакеты {#batches}

Пакеты здесь - собственные пакеты транспорта. Пакетный обработчик называет один размер в точке
монтирования, этот размер становится `MaxNumberOfMessages`, а один вызов `ReceiveMessage` - это один
пакет. На клиенте ничего не буферизуется.

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_batches.rs:handler"
```

Размер идёт в цепочке монтирования первым, а параметры очереди - за ним, как в примере выше. Пакет
приходит короче размера, если больше в очереди ничего не было. Пустым он не бывает: длинный опрос,
истёкший по времени, не даёт пакета вовсе.

`ReceiveMessage` возвращает не больше десяти сообщений за вызов, поэтому больший размер урезается до
десяти, и об урезании один раз пишется в лог для этой подписки.

У обработчика одиночных сообщений пакета нет. Его подписка всё равно запрашивает протокольный
максимум на каждый приём, потому что SQS тарифицирует запросы, а не сообщения, и отдаёт сообщения
обработчику по одному. Сколько их обработчик обрабатывает одновременно, задаёт `workers(n)` -
настройка фреймворка.

## Завершение доставки и отложенная повторная попытка {#settlement-and-deferred-retry}

Каждому способу завершить доставку соответствует встроенная операция SQS:

| Исход обработчика | Операция SQS |
| --- | --- |
| `HandlerOutcome::ack()` | `DeleteMessage` |
| `HandlerOutcome::retry()` | `ChangeMessageVisibility` в 0, и сообщение доставляется снова сразу |
| `HandlerOutcome::retry_after(delay)` | `ChangeMessageVisibility` в величину задержки |
| `HandlerOutcome::drop()` | `DeleteMessage` |

Отложенная повторная попытка тоже встроенная: `retry_after(delay)` ставит видимость сообщения
равной задержке, не больше протокольных 12 часов. Сообщение ждёт на месте и доставляется снова в той
же очереди с сохранённым счётчиком приёмов, потому что ничего не публикуется заново и копия не
создаётся.

Запасной путь самого фреймворка, который публикует отложенную копию заново, здесь поэтому не
работает никогда, и попросить о нём тоже нельзя: шаг `.out_retry(..)` на `SqsQueue` не
компилируется. Очередь уносит исчерпанную доставку сама, поэтому называть издателя со стороны
сервиса нечего, и ошибка компиляции говорит об этом и указывает на объявление ниже.

## Ограничение числа попыток {#capping-the-attempts}

Обработчик, который раз за разом просит повторить, гоняет своё сообщение по кругу, пока не
вмешается оператор. Этому кладут конец два шага сразу после `include`, и на любом брокере они
читаются одинаково:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_dead_letter.rs:mount"
```

В SQS эти два шага - одна настройка: политика перенаправления очереди. `max_attempts(n)` - это её
`maxReceiveCount`, `dead_letter(name)` - очередь, на которую она указывает, а записывает их на
очередь подписка, когда открывается. Дальше SQS сам считает приёмы и сам перекладывает сообщение,
и из сервиса ничего не уходит.

Очередь называют любым из двух способов. У регистрации, смонтированной по одному имени -
`#[subscriber("orders")]`, без дескриптора между нею и брокером, - нет своего места для
объявления, поэтому объявление забирает брокер и записывает ту же политику перенаправления на
очередь, которую это имя открывает.

Нужны обе половины, потому что половина политики перенаправления - это не политика. Регистрация,
которая объявила предел без адреса или адрес без предела, отказывается открыть подписку и называет
недостающую половину. К этому моменту очередь недоставленных сообщений должна существовать, если
только дескриптор не несёт `create_if_missing`, и она должна быть того же вида, что и очередь,
которой служит: у FIFO-очереди очередь недоставленных сообщений тоже FIFO.

Считает предел собственный счётчик SQS `ApproximateReceiveCount`, а он учитывает и текущую
доставку, поэтому первая попытка - это единица. То же число обработчик читает в заголовке
`sqs-receive-count` (`RECEIVE_COUNT_HEADER`) и может обойтись с последней попыткой иначе, чем с
первой.

Одна строка таблицы выше при объявлении читается иначе. Отбросить сообщение в SQS нельзя иначе как
удалив его, поэтому отказ удаляет; но доставку, которая исчерпала приёмы политики, вместо этого
возвращают в очередь, потому что попасть в очередь недоставленных сообщений она может только через
ещё один приём. Удаление на этом месте её потеряло бы.

## Продление видимости {#the-visibility-extender}

Обработчик может работать дольше, чем тайм-аут видимости сообщения, а вызова для продления аренды в
SQS нет. Пока доставленное сообщение живо, крейт взводит его видимость заново каждые полпериода, и
очередь не отдаёт то же сообщение второму воркеру, пока над ним работает первый. Взводится та
величина, под которой сообщение удерживается: названная дескриптором или собственный тайм-аут
видимости очереди, если дескриптор не назвал ничего. Этот тайм-аут читается у очереди один раз, при
открытии подписки, поэтому подписке без своего значения нужно право `sqs:GetQueueAttributes` на её
очередь, и без него она не открывается. Продление прекращается в тот момент, когда сообщение
завершено или уничтожено. Неудачное продление пишется в лог на уровне debug и повторяется на
следующем такте. Длительность работы обработчика ограничена процессом, а не тайм-аутом очереди.

Если доставленное сообщение уничтожено незавершённым, никаких дополнительных вызовов не происходит:
сообщение доставляется снова, когда истечёт его текущая видимость, - это и есть контракт
at-least-once.

## FIFO-группы сообщений {#fifo-message-groups}

У адресата на `.fifo` каждая отправка несёт идентификатор группы сообщений, потому что FIFO-очередь
его требует. Задайте его на каждое сообщение шагом [`group_id`](#per-message-settings) или закрепите
за всей позицией публикации на политике: `Publish::default().group_id("orders")`. Доставленное
сообщение приходит со своей группой в заголовке `partition-key`; в этом же заголовке сообщение может
назвать собственную группу - в записи, которая без изменений переносится на любой другой брокер.
Отправка, не назвавшая ничего, идёт под именем `"default"`.

Ответов может оказаться три сразу, и разрешаются они от самого частного: собственный шаг вызова,
затем заголовок `partition-key` сообщения, затем группа, закреплённая точкой монтирования.

Каждая отправка в FIFO подставляет ещё и идентификатор дедупликации, уникальный в пределах процесса,
если только вызов не назвал свой шагом `deduplication_id`. Явный идентификатор имеет приоритет над
дедупликацией по содержимому, поэтому две одинаковые полезные нагрузки, отправленные намеренно,
никогда не схлопываются в одну.

Обе настройки - настройки FIFO. Если назвать любую из них для стандартной очереди или темы,
публикация возвращает ошибку (`SqsError::NotFifo`): порядок, о котором просил вызывающий, там не
состоится, а молча отброшенное значение - ответ хуже. Заголовок `partition-key` - не просьба к
этому брокеру, поэтому стандартная очередь по-прежнему его игнорирует.

## Публикация {#publishing}

Политика публикации конструирует живого издателя, а рантайм инстанцирует его на подключённом брокере
при старте. Названная политика выбирает вид адресата:

- `SqsPublish` - политика, которая конструирует `SqsPublisher`: он отправляет прямо в очередь,
  названную по URL или по имени. Это же политика публикации брокера по умолчанию, поэтому
  отвечающий обработчик, смонтированный без собственной политики, отправляет через неё.
- `SnsPublish` конструирует `SnsPublisher`: он публикует уведомление в тему SNS, названную по ARN
  или по имени. Имя темы доходит до идемпотентного `CreateTopic` ровно так, как написано, поэтому
  тема адресуется тем именем, которое принимает сам SNS.

Тип ответа объявляет, куда идёт ответ: `#[outgoing(name = "..")]` на нём и есть адресат. Тип ответа,
который не объявил ничего, берёт адресата из клаузы `publish("..")` обработчика.

Точка монтирования называет, кто его туда доставит. `.out_reply(policy)` связывает её, а шаги после
вызова (`.codec(..)`, `.transform(..)`) относятся к этой позиции. Монтирование, не назвавшее
политики, оставляет `SqsPublish`, поэтому сервис из очереди в очередь пишет `b.include(handler);` и
ничего больше.
Отправить тот же ответ в тему вместо очереди - один шаг в цепочке:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sns_fanout.rs:reply"
```

Монтирование, которое её связывает, приведено в разделе
[Доставка через SNS всем подписчикам разом](#sns-fan-out). То же значение политики передаётся в хуки
жизненного цикла, `b.after_startup(Publish::default(), ..)`, - оттуда сервис публикует вне
обработчика.

Прелюдия экспортирует `SqsPublish` ещё и под именем `Publish` - именем, которое всякий брокерный
крейт даёт политике, принимаемой точкой монтирования и хуками жизненного цикла; в примерах написано
именно оно. `SnsPublish` сохраняет собственное имя: доставка всем подписчикам разом - отступление от
умолчания, а не само умолчание. Обе доступны и под именами с префиксом - для файла, где они
смешаны.

Издателя можно взять и у самого брокера: `SqsBroker::publisher()` до старта приложения,
`ConnectedSqsBroker::publisher()` и `ConnectedSqsBroker::sns_publisher()` - у подключённой формы.
Каждый из них пользуется соединением брокера совместно, и любая публикация после `shutdown`
возвращает `SqsError::NotConnected`.

### Настройки на сообщение {#per-message-settings}

Чем одно сообщение может отличаться от следующего, описывает `SqsPublishOptions`: идентификатор
группы сообщений и идентификатор дедупликации, оба необязательные. Билдер публикации принимает их
шагами из трейта `SqsPublishSteps`, который экспортирует прелюдия:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sqs_fifo_group.rs:publish"
```

Шаг - это позиция на билдере, а не обёртка вокруг издателя, поэтому завершённая им публикация
по-прежнему кодируется кодеком, который назвала точка монтирования, и проходит преобразования,
названные там же. Те же шаги есть на любой поверхности публикации: во внедрённом слоте `Out`, у
издателя, переданного в хук жизненного цикла, у издателя, взятого у брокера.

Тело обработчика, называющее шаг, - единственное место, где файл обработчика импортирует прелюдию
этого крейта вместо прелюдии фреймворка, и слот, через который оно публикует, ограничивается по типу
настроек:

<!-- inline-rust: the signature alone is the point here; a compiled snippet would drag in the slot marker, the payload type and a body that says nothing -->
```rust
async fn ship(
    order: &Order,
    Out(shipments): Out<impl Publisher<Options = SqsPublishOptions>, Shipments>,
) -> HandlerOutcome
```

Чего вызов не трогает, то остаётся закреплённым в точке монтирования:
`.out(Shipments, Publish::default().group_id("orders"))`. Ответ не поправляет ничего, потому что у
него нет точки вызова: политика, которую связал `.out_reply(..)`, и есть весь его ответ.

На выходе группа становится встроенным `MessageGroupId`, а не атрибутом сообщения, и доставленное
сообщение возвращает её в заголовке `partition-key`.

## Доставка через SNS всем подписчикам разом {#sns-fan-out}

SNS присутствует только как издатель: его адресаты доставки - очереди и HTTP-эндпоинты, а не
потребитель, которым владел бы этот крейт. Одна публикация в тему доходит до каждой подписанной
очереди, а каждую очередь читает обычная подписка `SqsQueue`.

`subscribe_queue_to_topic` подключает очередь к теме с сырой доставкой сообщений, поэтому полезные
нагрузки и заголовки приходят развёрнутыми, обычными сообщениями SQS, а не внутри конверта SNS:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sns_fanout.rs:wiring"
```

Администрирование топологии идёт по собственной последовательности переходов жизненного цикла
брокера, а не через билдер приложения; в бою тему и её подписки заводят как инфраструктуру. В примере
они связываются из хука `after_startup`, где очереди уже существуют, потому что их открыли подписки,
затем в очередь кладётся один заказ, и ответ обработчика доставляется всем подписчикам разом.
`.out_reply(SnsPublish::default())` - это всё, что нужно связать для такой доставки:

```rust
--8<-- "crates/ruststream-sqs-sns/examples/sns_fanout.rs:app"
```

## Сгенерированный документ {#the-generated-document}

Фреймворк генерирует документ AsyncAPI по объявлениям сервиса, а этот крейт дописывает в него то,
что знает только SQS. У этого своя фича, и она включает фичу ядра:

```toml
ruststream-sqs-sns = { version = "0.7", features = ["asyncapi"] }
```

После этого каждый канал, который открывает дескриптор очереди, несёт канальную привязку `sqs`:

```json
--8<-- "crates/ruststream-sqs-sns/tests/asyncapi_channel.json"
```

`name` и `fifoQueue` берутся из имени очереди: очередь делает FIFO-очередью именно суффикс
`.fifo`. `visibilityTimeout` и `receiveMessageWaitTime` берутся из параметров опроса, названных в
дескрипторе. Параметр, который дескриптор оставил очереди, не угадывается, а опускается: чтобы его
прочитать, нужно соединение, а документ строится до того, как что-либо подключилось. По той же
причине в документе никогда не появляется ARN очереди, а политика доступа к очереди - это
инфраструктура, а не описание сервиса. Не появляются в нём и учётные данные, даже когда брокер
настроен по URL, который их несёт.

Предел и адрес недоставленных сообщений, объявленные регистрацией, сообщает сам фреймворк: на
операции приёма и как канал, в который регистрация отправляет.

Позиция публикации тоже описывает своё назначение. Фреймворк передаёт политике то имя, которое
документ сообщает как адрес канала, поэтому ответ через `SqsPublish` несёт привязку `sqs` с полями
`name` и `fifoQueue` очереди, а ответ через `SnsPublish` - привязку `sns` с полем `name` темы. Тема
с суффиксом `.fifo` сообщает `ordering.type` как `FIFO`, а `ordering.contentBasedDeduplication` как
`false`: каждая FIFO-отправка этого крейта несёт собственный идентификатор дедупликации, а явно
названный идентификатор важнее того, который тема вывела бы сама. Стандартная тема не сообщает
порядок вовсе, и спецификация читает это как отсутствие порядка. Параметры опроса остаются на
половине канала, принадлежащей подписке: у позиции публикации их нет.

Крейт описывает один сервер, с протоколом `sqs`: брокер описывает один, а публикации в SNS идут в
тот же аккаунт и тот же регион и пользуются им же.

## Полезные нагрузки и заголовки {#payloads-and-headers}

Каждый заголовок становится одним атрибутом сообщения SQS: `String` для значения, которое SQS
принимает как текст, `Binary` для остальных. Никакого формата конверта не изобретается, поэтому то
же сообщение прочитает любой другой отправитель или получатель SQS. Значение заголовка - байты по
обе стороны от `HeaderMap` фреймворка, поэтому сервису не видно, который из двух типов атрибута его
перенёс.

`partition-key` - единственный заголовок, который атрибутом не становится. Адресат на `.fifo`
отправляет его встроенным `MessageGroupId`, и доставленное сообщение приносит его обратно;
стандартный адресат его отбрасывает, поэтому стандартная очередь его не передаёт и не возвращает.

Тело - единственное ограничение транспорта. Тела сообщений SQS текстовые, и текстом там считается
меньше, чем в UTF-8: управляющие символы C0, кроме табуляции, перевода строки и возврата каретки, не
принимаются, как и два не-символа в конце основной плоскости. Полезная нагрузка, которую SQS
принимает, проходит без изменений. Всё остальное кодируется в base64 с атрибутом-меткой и
раскодируется обратно при приёме: двоичная нагрузка и наравне с ней корректная UTF-8, несущая эти
символы, - именно такую часто выдаёт двоичный кодек. То же правило выбирает тип атрибута для
значения заголовка, поэтому публикацию никогда не отклоняют из-за байтов, которых SQS не принимает.

Обработчик может разобрать тело сам - для очереди, которую наполняет отправитель вне этого
фреймворка, или для формата передачи без модели `serde`: newtype с `#[derive(Deserialized)]` над
`&[u8]` идёт по байтовому пути фреймворка, без кодека где бы то ни было. Шаг base64 к этому моменту
уже отменён, поэтому обработчик видит те байты, которые отправил отправитель.

## Локальная разработка с LocalStack {#local-development-with-localstack}

В репозитории лежит compose-файл LocalStack со службами `sqs` и `sns` и рецепты `just` вокруг него:

```bash
just brokers-up                 # запустить LocalStack на 127.0.0.1:4566
cargo run --example sqs_service
cargo run --example sqs_batches
cargo run --example sqs_fifo_group
cargo run --example sqs_dead_letter
cargo run --example sns_fanout
just brokers-down
```

Направьте брокер на стенд через `endpoint`, `test_credentials` и явный `region`, как это сделано в
примерах. Набор живых тестов запускается, когда задан `SQS_TEST_ENDPOINT`, и пропускается, когда не
задан:

```bash
just test-brokers               # поднять LocalStack, интеграционные тесты и conformance, погасить LocalStack
```

или по уже запущенному стенду:

```bash
SQS_TEST_ENDPOINT=http://127.0.0.1:4566 cargo test --workspace --all-features -- --test-threads=1
```

CI прогоняет тот же набор по LocalStack на каждое изменение.

Каждый набор conformance, оправданный совместимостями этого крейта, прогоняется дважды: по
внутрипроцессному транспорту и по стенду. У последовательности переходов жизненного цикла и у
`capabilities::batches` есть оба прогона; набор маршрутизации идёт только внутри процесса. У
`request_reply`, `transactions`, `owned_transactions` и `seeking` здесь нет ни одного
прогона - в SQS нет канала запрос-ответ, нет транзакций и нет курсора для перемотки, поэтому
крейт не реализует ни одну из этих совместимостей и их наборы неприменимы.

## Тестирование {#testing}

Фича `testing` поставляет `SqsTestBroker`: внутрипроцессный брокер, который воспроизводит основную
маршрутизацию крейта без сервера и без сети, по той же последовательности переходов, что и
настоящий, - включая остановку, на которой издатель, разделявший соединение, сообщает
`NotConnected`, а не маршрутизирует в очищенный роутер. Он лежит в модуле `testing` этого крейта, и
файл теста импортирует его по имени: `use ruststream_sqs_sns::testing::SqsTestBroker;`.
Соберите приложение на нём, и обвязка `TestApp` прогонит ваши настоящие обработчики, кодеки и
middleware: опубликуйте вход, а затем проверьте, что получил обработчик и что он опубликовал дальше.
См.
[что может утверждать тест](https://docs.rs/ruststream/latest/ruststream/testing/index.html#what-a-test-can-say).

Объявление, которое поставляет сервис, монтируется там без изменений. `SqsQueue` - источник подписки
и для внутрипроцессного транспорта, поэтому `#[subscriber(SqsQueue::new("orders").wait(..))]` и
настройки точки монтирования, пристроенные к нему цепочкой, выполняют ту же связку, что выполняет
сам сервис. Параметры останавливаются на дескрипторе: внутри процесса нет длинного опроса, который
ограничивал бы `wait`, нет часов повторной доставки, которые взводил бы `visibility`, и нет очереди,
которую создавал бы `create_if_missing`.

Половина, отвечающая за публикацию, совпадает. `SqsPublish` и `SnsPublish` конструируют издателя и
против внутрипроцессного транспорта, который называет `SqsPublish` своей политикой по умолчанию,
поэтому `.out_reply(Publish::default())` и ответ по умолчанию у обработчика с `publish(..)`
монтируются как написаны. Настройки на сообщение доходят и туда: шаг, названный телом обработчика,
добирается до издателя внутрипроцессного транспорта так же, как до настоящего, обвязка его
записывает (`tb.out::<Shipments>().assert_called_once().with_options(..)`), а разрешённая группа
доставляется в заголовке `partition-key` ровно так, как её доставляет SQS. Обе политики конструируют
один и тот же `SqsTestPublisher`,
потому что у роутера нет темы, от которой шла бы доставка всем подписчикам разом: тест доказывает,
что ответ ушёл по адресу, который называет политика, а не что SNS доставил его дальше в очереди,
подписанные на эту тему.

Маршрутизирует он по точному имени очереди, а на способ завершения отвечает целиком, вместе с
задержкой и с пределом. `retry_after` придерживает сообщение и отдаёт его той же подписке, когда
задержка прошла, поэтому в тесте её проматывает `tb.advance(..)`, а отложенная копия фреймворка
остаётся в стороне от пути этого брокера и внутри процесса, и в бою. Приёмы он считает так же, как
их считает очередь, а политика перенаправления регистрации перекладывает исчерпанную доставку в
очередь недоставленных сообщений, где её читает `tb.published::<Invoice>("invoices-dead")`. Что
относится к самой очереди (тайм-аут видимости, который истекает сам собой, порядок FIFO и доставка
через SNS всем подписчикам разом), проверяет набор живых тестов по LocalStack.

Пакеты - единственное место, где два транспорта различаются внутри: внутри процесса их собирает
клиентский буфер фреймворка, а настоящий подписчик берёт их из `ReceiveMessage`. Точка монтирования
называет размер и в обоих случаях получает пакеты не больше этого размера, - благодаря этому
пакетный обработчик вообще можно тестировать внутри процесса.
